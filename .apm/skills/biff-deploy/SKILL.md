# Deploy a Biff App

Biff 2 deploys with the `biff.tasks` tasks that every starter project includes: `clojure -M:run prod-setup` provisions an Ubuntu server once, `clojure -M:run deploy` pushes the current git branch to it and restarts the app, and `clojure -M:run uberjar` builds a standalone jar for other hosting. Run this skill from inside a Biff 2 project (one whose `deps.edn` has a `:run` alias using `com.biffweb.tasks.app`).

## Arguments

| Input             | Target                                                                                  |
|-------------------|-----------------------------------------------------------------------------------------|
| (no argument)     | VPS path: `clojure -M:run prod-setup` (first time only), then `clojure -M:run deploy`           |
| `vps`             | Same as (no argument); explicit selection of the VPS path                               |
| `soft`            | `clojure -M:run deploy --soft`: push, then evaluate every project source file in the running app without a restart |
| `uberjar`         | Build `target/jar/app.jar` with `clojure -M:run uberjar`                                    |
| `all`             | Same as (no argument); accepted for family consistency                                  |
| `--report`        | Print the planned commands and the facts they depend on (domain, deployment name, branch and worktree state, uploaded untracked files, or the jar path). Write nothing, run nothing. |

This skill operates on deployment-target keywords rather than file paths, so the `<path>` row of the standard scope vocabulary does not apply.

## Mutation

Mutates by default: provisions a server and deploys to production (VPS and soft paths) or writes a jar under `target/` (uberjar path). The VPS and soft paths also ask the operator for confirmation before each remote-touching command, layered on top of the standard mutate-on-invoke contract; treat any refusal at that prompt as a stop. With `--report`, the skill prints the planned command sequence for the selected path and writes nothing.

## Steps

Parse `$ARGUMENTS`. Extract `--report` if present (report-only mode). Use the remaining token as the deployment target. If the remaining token is empty or `all`, default to `vps`.

Read the deployment settings from `resources/config.edn` and the local `config.env`:

| Setting | Source | Notes |
|---------|--------|-------|
| `:biff.tasks/domain` | `DOMAIN` in the local `config.env` | Required. The deploy tasks run on the developer's machine and read the domain there, so it does not go in `config.prod.env`. The server is reached as `root@<domain>` for setup and `<deployment-name>@<domain>` afterwards. |
| `:biff.tasks/deployment-name` | `DEPLOYMENT_NAME`, default in `config.edn` | Linux user, home directory, and systemd service name on the server. |
| `:biff.tasks/deploy-untracked-files` | `config.edn` | Gitignored files copied after the push. Only committed files and the files listed in this setting reach the server, so add any new gitignored file the app needs at runtime here. The starter copies the built CSS and uploads `config.prod.env` as the server's `config.env`. |
| `:biff.tasks/nrepl-port` | `NREPL_PORT`, default 7888 | Used by `prod-nrepl` and `deploy --soft`. |

Under `--report`, do not run any task. Print the selected path, the resolved domain and deployment name, the current branch, whether `git status --porcelain` is empty, whether HEAD is detached, the untracked-file list, and the command sequence below. For the uberjar path, print `target/jar/app.jar` and the `java -jar` command.

### VPS path (default)

#### Confirm before acting

Every command in this path touches a remote host or production. Show the user each command and the target host, and wait for confirmation before running it. Treat refusal as a stop.

#### First-time provisioning

Skip this section when the server already runs the app (ask the user if unsure).

1. Confirm `DOMAIN` is set in the local `config.env` and that an A record for it points to the server.
2. Confirm `ssh root@<domain>` succeeds. The server should be a fresh Ubuntu machine; the setup script is only tested on Ubuntu.
3. Confirm `config.prod.env` is filled in for production: `COOKIE_SECRET` (generated by `init`), the `LITESTREAM_*` backup keys, the MailerSend keys for sign-in email, the Turnstile keys for the captcha, and optionally `ALERT_EMAIL` and `ADMIN_USER_ID`. Litestream needs `LITESTREAM_ACCESS_KEY_ID`, `LITESTREAM_SECRET_ACCESS_KEY`, and `LITESTREAM_BUCKET`, and it stays off while `LITESTREAM_ACCESS_KEY_ID` is blank. Production does not set `SKIP_CAPTCHA`, so the captcha check runs and needs both Turnstile keys. Without them the app starts, but every sign-in request returns a 500 ("Captcha is not configured"). Without `MAILERSEND_API_KEY`, the starter's `send-email` prints sign-in codes to the server log instead of emailing them.
4. Provision:

   ```bash
   clojure -M:run prod-setup
   ```

   The script upgrades every installed package, installs packages including `default-jre`, git, and `rlwrap`, and installs the Clojure CLI and trenchman; creates the deployment user with root's SSH keys; creates a systemd service running `clj -M:prod` with its own `PORT`; installs Caddy as an HTTPS reverse proxy for the domain; and enables the ufw firewall allowing only SSH, HTTP, and HTTPS. `clj -M:prod` is quoted from the script's `ExecStart` line. It works on the server because the script installs `rlwrap`, which the `clj` launcher requires. `clojure -M:run prod-setup --copy-only` copies the script without running it, for review.

5. After setup, check that the server's Java is version 21 or later (`ssh <deployment-name>@<domain> java -version`). Biff 2 requires it, and the version that `default-jre` installs depends on the Ubuntu release.

#### Deploy

Deploy requires a clean worktree and a branch checked out (not a detached HEAD). Check `git status --porcelain` first and stop if it is not empty; ask the user to commit or stash rather than doing either yourself. Untracked files count: the starter's `start` writes `graph.mmd` on every local run, and a project-scope APM install adds `apm.yml`, `apm.lock.yaml`, a `.gitignore` change, and skill folders under `.agents/skills/` and runtime folders such as `.kiro/` and `.grok/`. Ask the user to commit each of these or add it to `.gitignore`.

```bash
clojure -M:run deploy
```

`deploy` builds minified CSS, force-pushes the current branch to `/home/<deployment-name>/repo` on the server, copies the untracked files, and restarts the service. The force-push replaces the server's copy with whatever branch is checked out locally. There is no branch setting.

### Soft path

```bash
clojure -M:run deploy --soft
```

Same push and file copy, but instead of restarting, it runs `trench` on the server to load every project source file, in dependency order, into the running app through nREPL on `:biff.tasks/nrepl-port`. Use it for code changes that do not touch startup-only code (schema columns, `start-order`, dependencies); otherwise run the VPS path. Confirm before running, as for the VPS path.

Before the first soft deploy, check that the main namespace's `start` returns the system map. The starter's `start` ends with `(spit "graph.mmd" ...)` and returns nil, so its `-main` starts nREPL on a random port and the soft deploy cannot connect. Ending `start` with `@system` restores the configured port, and the change takes effect after one full VPS deploy.

### Uberjar path

```bash
clojure -M:run uberjar
```

This writes `target/jar/app.jar`. Run it with the production configuration in a `config.env` in the working directory, or with the same variables in the environment:

```bash
java -jar target/jar/app.jar
```

The app listens on `PORT` (default 8080) and `HOST` (default `localhost`; set `HOST=0.0.0.0` inside a container). The host must provide Java 21 or later.

## Post-deploy verification

```bash
clojure -M:run prod-logs 100   # follows the service log; stop it once startup is confirmed
curl -fsS -o /dev/null https://<domain>/
```

`prod-logs` runs `journalctl -f` over SSH and does not exit on its own; run it with a timeout or in the background and stop it after reading the startup lines. Report a successful deploy only after the curl check passes. `clojure -M:run prod-restart` restarts the service, and `clojure -M:run prod-nrepl` opens an SSH tunnel to the production nREPL on `:biff.tasks/nrepl-port`, which works only when `start` returns the system map (see the soft path).

## Gotchas

- **Never run `prod-setup` against a server already serving other things without explicit confirmation.** It upgrades every package, enables ufw with only SSH, HTTP, and HTTPS open, overwrites `/etc/systemd/journald.conf`, and adds the domain to the Caddyfile.
- **Several apps can share one server** when each uses a different `DEPLOYMENT_NAME` and domain; `prod-setup` assigns each its own port.
- **The starter `Dockerfile` is outside this skill.** Its build stage runs `RUN clj -M:dev uberjar` (quoted from the starter `Dockerfile`), but the starter defines no `:dev` alias. `clojure -M:run uberjar` is the working command if the user maintains a Docker build.
- **Production data lives in SQLite on the server's disk.** Fill in the `LITESTREAM_*` keys in `config.prod.env` (read into the `:biff.sqlite/litestream-*` keys) before relying on the server for real data.
